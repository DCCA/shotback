# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Required reading before edits

Read `FIREHOSE.md` before making any change — it is the project's operating contract (OpenSpec-lite: fluid, iterative, brownfield-first, one logical unit of work per change). If `FIREHOSE.md` conflicts with another local guideline, `FIREHOSE.md` wins unless the user overrides it. `AGENTS.md` and `CONTRIBUTING.md` restate the same workflow.

Non-trivial work is tracked as a change folder under `.docs/`: `proposal.md` (why/scope), `spec.md` (RFC-2119 requirements with Given/When/Then scenarios), `design.md` (how), `tasks.md` (checklist). Move `todo/ → doing/ → done/` and add a `completion-summary.md` when finishing. `.docs/PRD.md` is the product entry point. `.docs/` is source-of-truth — never gitignore it.

## Architecture

A Manifest V3 Chrome extension (TypeScript + React 18 + Vite + Tailwind). Two HTML entry points (editor, viewer) plus two extension scripts, all bundled by `vite.config.ts` (which fixes `background.js`/`content.js` output names so the manifest can reference them). `@/*` aliases `src/*`.

**Three surfaces:**

- The toolbar icon has **no popup**: `src/background.ts`'s `chrome.action.onClicked` handler opens the editor in a new tab with `?tabId=&windowId=&autocapture=1` of the active tab, and the editor auto-captures once on load (one-click capture). The manifest's `commands` entry (`_execute_action` for `Alt+Shift+S`) binds a keyboard shortcut to the same handler.
- `src/editor/main.tsx` is the editor's **composition root** (~200 lines): it reads the URL params, wires the capture and inspection round trips, and renders the pieces the work actually lives in - `annotation-canvas.tsx` (drawing, selection, the inline comment editor, the crop preview and controls, the keymap), `tool-palette.tsx` (the canvas toolbar, see below), `sidebar.tsx` (general feedback, prompt detail, export format, the two keyboard-hint lines and the output buttons, grouped and ranked - see the outputs paragraph below - tool, colour and zoom moved out to the palette), `comment-timeline.tsx` (the numbered rows), `saved-shares.tsx` (the stored shares, re-capture and the batch handoff), `status-toast.tsx` (the one *visible* aria-live region, see below), plus the two hooks that hold everything else: `use-editor-state.ts` (state, prefs, undo/redo) and `use-exports.ts` (every output, including `exportView`). `main` itself is a **fixed two-pane app shell** from `lg` up (`lg:h-screen lg:min-h-0 lg:overflow-hidden`): the window never scrolls, the sidebar column and the canvas card each scroll their own contents (`lg:min-h-0` on both - a grid item stretches by default, and without it `overflow-y-auto` grows the row instead of scrolling), and `#capture-viewport` is the **only** scroller for the capture. The canvas track is `minmax(0,1fr)`, **not** `1fr`: a bare `1fr` carries an automatic minimum, so anything inside the canvas card that refuses to shrink (the tool palette, before it was allowed to wrap) widens the column, overflows the window and clips the capture inside it - the explicit 0 minimum is what keeps the pane's width a property of the window rather than of its contents. Below `lg` the shell unwinds: the canvas is `order-1` and the sidebar `order-2` so the capture comes first, and the window scrolls normally. That is **visual order only** - DOM order is unchanged, so tab order and screen-reader order are as before.
- `src/viewer/` - renders a saved share from `?share=<id>` (local-only page). When that share carries a `previousShareId` and the earlier share is still stored, it renders the two captures side by side, labelled **Before** and **After** (see the re-capture paragraph below).
- `src/background.ts` - service worker; logs on install and hosts the `chrome.action.onClicked` handler (one-click capture). `src/content.ts` - injected on `<all_urls>`; responds to `SB_GET_PAGE_METRICS` / `SB_SCROLL_TO` / `SB_RESTORE_SCROLL`, to the capture-notice messages `SB_CAPTURE_BEGIN` / `SB_SET_OVERLAY` / `SB_CAPTURE_END`, to `SB_INSPECT_POINTS` (per-annotation DOM context) and to `SB_GET_DIAGNOSTICS` (the page's failed requests).

**Status toast (`src/editor/status-toast.tsx`):** the editor's one **visible** `aria-live="polite"` region, floated over the canvas pane rather than rendered in the sidebar's scroll flow, where it was routinely off screen under nine export buttons at the moment it mattered. It reads `status`/`progress` off `EditorState` and owns no state of its own: a **success clears itself after 4s** (`setStatus(null)` on a timer keyed by the status **object**, not by its text - every `setStatus` builds a fresh object, so an identical message arriving twice is a new identity and gets its own full 4s instead of inheriting the previous timer's remainder; `setStatus` is `useState`'s stable setter, so an unrelated render cannot restart the clock), an **error persists** until its dismiss button is pressed, and progress rides alongside - `main.tsx` clears it in the capture's `finally`, so the old stale `Capture completed` is gone. It is `fixed bottom-4 right-4` with `lg:absolute` inside the canvas `Card`: absolute where the canvas pane is always on screen, fixed below `lg` where the card itself can be scrolled away. **Bottom-right, not top-right**: the tool palette is docked along the top of the same card, so a toast up there covered the colour swatches (or, at a wider window, the Zoom select) and - being `pointer-events-auto` - swallowed clicks aimed at them for the whole 4s a success is up; the bottom-*left* corner is the applied-crop chip's, so the toast takes the other one. The e2e checks all three: inside the canvas pane's box, below the swatch row, and `elementFromPoint` over a swatch returning the swatch. The status paragraph keeps `font-medium` - that is what separates it from the progress line, and what the e2e waits on.

There is a **second** live region, and it is never shown: one `sr-only` `role="status"` paragraph (`#editor-announcer`) in `main.tsx`, fed by `EditorState.announcement`. Delete, undo and redo change only the canvas and the timeline, so they used to succeed in silence for anyone not watching the pixels; they now announce `Annotation deleted` / `Undo` / `Redo` there. They deliberately do **not** go through the toast - a banner over the capture on every keystroke of an undo run is noise, and the toast stays the exports' surface. `announce()` in `use-editor-state.ts` alternates a trailing no-break space, because a live region handed the same string twice sees no DOM change and says nothing the second time. Icons are inline SVG paths inheriting `currentColor` (never emoji, which would carry the platform's own colour onto a themed surface); the entrance is a `transition-[transform,opacity]` flipped on the first frame after mount, with a targeted rule in the stylesheet's `prefers-reduced-motion` block collapsing it to 0ms.

**Canvas tool palette (`src/editor/tool-palette.tsx` + `src/lib/tool-palette.ts`):** a toolbar docked _inside_ the canvas card, above `#capture-viewport` - one 48px row where there is room, wrapping into as many rows as it needs at **every** width (including inside the tool group itself), because a segment hidden off the right edge is worse than a second row - every control on it changes what the **next pointer gesture** does, so it belongs where the pointer is rather than in the sidebar. Wrapping is also load-bearing rather than cosmetic: eight segments are wider than a narrow canvas pane, and a toolbar that refuses to shrink widens the pane and clips the capture in it (which is also why `main`'s grid track is `minmax(0,1fr)` and not a bare `1fr` - see the shell paragraph above). It holds one real segmented control (a single bordered group with hairline dividers, the active segment filled `bg-primary text-primary-foreground`, a `kbd` hotkey suffix on each), six stroke swatches plus a custom-colour disc, and the zoom `Select`. The two old sidebar dropdowns (Interaction, Tool), its Zoom row and its native colour `Input` are gone. With no capture yet the segments and the swatches are **disabled** (one `opacity-50` on each group, so the dividers fade with them and the token `color` the contrast sweep reads is untouched) and the hotkeys are guarded to match - there is nothing for a tool to act on. Zoom stays live: it is a property of the view, not of a gesture.

The **state model** is unchanged underneath - the canvas still reads `tool` and `interactionMode` - but the UI now writes them through one setter, `setPaletteTool(segment)` in `use-editor-state.ts`: `select` is move mode, and **every other segment is that tool in draw mode**. That is the _only_ writer - `setInteractionMode` is not on `EditorState` at all, so the compiler holds the invariant rather than a convention (the comment timeline's row click enters Select through the same setter). That is what the old "picking Crop or Redact forces draw mode" special case becomes once every tool is on the same control; a tool that could be picked into a mode that cannot draw it was only ever a bug. `activeSegment(tool, interactionMode)` (pure, in `src/lib/tool-palette.ts`) derives the lit segment back out, so the palette can never disagree with the cursor.

`commitNewAnnotation` **no longer flips to move mode**. A drawing tool stays selected after each shape, so five boxes are five drags; what changes is the _selection_ (the new annotation is selected and its inline comment editor focused, as before), and clicking an existing annotation still selects it for editing whatever the mode - `onAnnotationPointerDown` sets `selectedId` before it checks for a drag. The one-window keydown listener in `annotation-canvas.tsx` binds the hotkeys - `V B A T H P R C` - through `hotkeyTool(key)` (single characters only, no modifier - `Ctrl+C` is a copy, not the crop tool) behind the same `isTyping` guard as the rest of the keymap **plus a `closest('[role="combobox"],[role="listbox"]')` check**: the comment editor is a `<textarea>` on the canvas, so an unguarded `b` would swallow every letter of a note - and `Select` is a listbox built on a `<button>`, not a form field, whose typeahead reads plain keydowns, so without the second check typing `a` for "Actual size" in Zoom would also pick the Arrow tool.

**The canvas is drawable from the keyboard.** The SVG overlay carries `tabIndex={0}` (its accessible name says what the keys do, and the browser's own focus ring is left as the indicator), and with it focused **Enter places the armed tool's default shape** at the centre of the *visible* part of the capture - `visibleCentre()` intersects `#capture-viewport`, `#capture-window` and the image, so a shape lands where the user is looking rather than at the top of a 6000px capture. Rectangles are `KEYBOARD_SHAPE_SIZE` (160x100) clamped inside the image, an arrow is a ~140px diagonal, a text is an anchor, and Crop drops a marquee that Enter then applies. **Pen is deliberately excluded**: a stroke is a path the hand draws, and a default squiggle is a shape the user never made. Placement goes through the same `commitNewAnnotation` + `onCommit` a pointer-up does, so there is one creation path - selection, comment focus, undo entry and DOM inspection all come free. **Arrow keys nudge the selection by `KEYBOARD_NUDGE` (8px) and Shift+arrow resizes** the three rectangle tools; both read the selected annotation through `getAnnotations()` (the ref) because the window listener is not re-bound per annotation change, and **the commit is on key-up**, not keydown - a held key repeats, and twenty history entries for one nudge would make undo useless.

**Escape in the inline comment editor discards the draft.** It restores the note as it stood when the textarea took focus (`noteBaselineRef`, recorded `onFocus` so re-entering an existing note and bailing restores *that* note), clears `noteDirtyRef` so the unmount cleanup writes no history entry either, and then puts focus back on the canvas. Every other leave path still commits, `onBlur` included. It was the one control in the editor where Escape meant the opposite of cancel: the handler blurred the textarea and `onBlur` shipped whatever had been typed. **Leaving the editor no longer strands the keyboard on `<body>`** either: `restoreFocusAfterNote` (called from `onBlur` and from the selection-change cleanup) moves focus to that annotation's comment-timeline row (`[data-annotation-row]`), falling back to the canvas - deferred a frame and only when focus was really orphaned, the same rule `useTimedConfirm` restores a trigger by, so it can never yank the caret out of something the user moved into. Tool hotkeys stay off the textarea; the sidebar's second keyboard-hint line states both halves, because none of it is discoverable from a control.

`src/lib/tool-palette.ts` also owns `SWATCHES` - the **one** place the six annotation hex colours live. They are _data_ (written into every annotation, the exported PNG and the saved share), not Tailwind classes and not themeable, so the discs take an inline `backgroundColor` and the custom disc an inline conic-gradient built from `SWATCHES` itself. They are also the reason the repo-wide colour grep below is about **Tailwind colour utilities**, not about hex strings: each disc carries a hairline `inset` shadow plus a 6px `bg-foreground/40` core, which - because `--foreground` is by definition the opposite end of the theme from `--card` - is faint on a mid-tone swatch and unmistakable on `#111827` against the dark card, where the rim alone still read as an empty slot. `DEFAULT_ANNOTATION_COLOR` is the first swatch, `#ef4444` - **the old `#ff3333` default is retired**.

**Full-page capture flow** (`src/lib/capture.ts`, called from the editor - _not_ from the background): `activateTab` brings the target tab forward → `ensureInjectable` re-injects `content.js` → reads page metrics → `buildScrollSteps` computes viewport-sized scroll offsets → for each step, scrolls the page (via content-script message) and calls `chrome.tabs.captureVisibleTab` → stitches the PNG segments onto a single canvas scaled by `devicePixelRatio`. Restores scroll and the previously-active tab in `finally` blocks. `CaptureResult` also carries a `CaptureEnvironment` - the captured tab's page title, URL, viewport (CSS px), device pixel ratio, colour scheme, scroller kind and user agent plus the capture timestamp - built by the pure, unit-tested `buildEnvironment(metrics, userAgent, now)`. Everything but `userAgent`/`capturedAt` comes from `PageMetrics` (the content script measures the _target_ tab; the editor page has its own title, size and scheme). The editor keeps it in `environment` state (cleared when a capture starts) and hands it to both prompt builders and to `saveLocalShare`, which stores it as an optional passthrough field - no `schemaVersion` bump, absent on older shares.

**Capture modes:** `captureFullPage` takes a fourth argument, `CaptureOptions = { mode?: "full" | "visible"; delaySeconds?: number }`, both defaulting to today's behaviour. The sidebar's **split control** - the unchanged filled `Capture Page` button beside a compact `Select` - offers the three useful combinations (`CAPTURE_MODES`: Full page / Visible area / Full page after 3s), mapped by the pure `captureOptions(mode)`. The mode is local `useState` in `sidebar.tsx`, read once at the click and handed to `main.tsx` through `onCapture(mode)`, because nothing else in the session depends on it. **`visible` changes exactly three things** inside the orchestrator: `steps` is `[0]`, the stitched canvas is sized off `metrics.viewportHeight` instead of `fullHeight`, and the per-frame `SB_SCROLL_TO`/`SB_SET_OVERLAY` pair is skipped. The metrics read (which is what hides the page's scrollbars), the diagnostics read and the `SB_RESTORE_SCROLL`/`SB_CAPTURE_END` teardown all still run, so a visible capture leaves the page exactly as a full one does. It shows **no notice**, deliberately: one `captureVisibleTab` call neither takes the tab over for seconds nor scrolls it, and the notice's show/paint/hide-acked-after-paint/settle sequence would flash half a second of warning about something already finished. It still sends one `SB_SET_OVERLAY` before its frame, which is both the hide for a notice a countdown may have left up **and** the paint barrier the frame loop gets: the ack waits for the next paint, which is what guarantees the hidden scrollbars have landed. Its `CaptureResult` also carries `scrollOffset` - the scroll position it was taken from, 0 for a full capture - because a visible image's top is _not_ page y 0; see the DOM-context paragraph below. **The delay's countdown is driven by the orchestrator**, not the content script: `SB_CAPTURE_BEGIN` takes an optional `heading` and is re-sent once a second with `captureNoticeHeading(remaining)` ("Capturing in 3...", "2...", "1..."). The post-countdown begin **always supplies `captureNoticeHeading(0)`** rather than letting the notice keep whatever it last said - the content script only rewrites the heading when one is given, so omitting it left "Capturing in 1..." on screen for the whole stitch. The content script only sets the text of its `[data-shotback-heading]` node, so it holds no timer that a failed capture could leave running, and the wording is a pure function with its own unit test. It is text updates only - no animation - so `prefers-reduced-motion` is unaffected. **Modes are editor-side only**: `background.ts` is untouched and `main.tsx` passes `"full"` explicitly for the `autocapture=1` path, because there is no moment between the toolbar click and the capture in which a mode could be chosen.

**Highlight and Pen (mark up, rather than point at):** two annotation types beside box/arrow/text, both fully note-carrying (unlike `redact`, which is mute by design) - numbered pins, inline comment editor, DOM inspection, crop, export, sidecar and prompt lines. `HighlightAnnotation { tool: "highlight"; x; y; width; height }` is a rectangle, so it joins `RectAnnotation` and inherits the eight-handle resize path; `PenAnnotation { tool: "pen"; points: Array<{x,y}> }` is a freehand path **thinned as it is drawn** (a point only once the pointer has moved `PEN_POINT_SPACING`, 3px, from the last one), so a stroke is a few dozen points rather than one per pointer event in the annotations array, the undo history, every saved share and the sidecar; a single-point path is a click that never moved and commits nothing. A pen stroke has no rect of its own, so `annotationBounds` derives one from min/max of its points (a zero rect when there are none, not the `Infinity` a bare `Math.min` of nothing yields) and that bounds is what `pinAnchor`, `inspectAnchor` (its centre), `applyCrop` and `describeGeometry` all read. **`applyCrop` treats pen like an arrow, not like a box**: kept when _any_ point is inside, then shifted, never clamped - pulling a stray point onto the crop edge would redraw the stroke into a shape the user never made. A highlight is intersected like a box. `describeGeometry` renders a highlight exactly like a box and a pen as `pen path of N points from (x1, y1) to (xn, yn) px [..% of page]`. **The highlight's wash is `multiply` at `HIGHLIGHT_ALPHA` (0.35)** - `mix-blend-mode` on the canvas, `globalCompositeOperation` + `globalAlpha` (saved and restored) in the export - because that keeps the text underneath readable instead of washing it out. But multiply against a near-black section leaves near-black, so the region **also** gets a `HIGHLIGHT_EDGE_WIDTH` (2px) edge at full opacity, outside the blend: on light content it reads as the marker's own boundary, and on dark content it is the whole of what marks the region (measured on a two-tone fixture - without it a highlight over a dark hero was invisible in both themes). Both constants are exported from `annotate.ts` and used by the canvas, so the preview and the PNG cannot drift. Pen draws as a round-capped, round-joined polyline in both, over a 14px transparent stroke on the canvas for a hit area - the same trick the arrow uses.

**Page diagnostics:** right after the metrics read, `captureFullPage` also asks the tab for `PageDiagnostics` via the best-effort `getDiagnostics(tabId)` (`SB_GET_DIAGNOSTICS`; any failure yields an empty list, never a failed capture). The content script computes it on demand from `performance.getEntriesByType("resource")`, keeping entries whose `responseStatus` is 400 or more - feature-guarded on `typeof responseStatus === "number"`, deduped by status+URL, capped at 20, each URL collapsed to one line of 200 chars because it is page-controlled text. It is a **partial view by construction**: `responseStatus` is CORS-gated (0 for a cross-origin response with no `Access-Control-Allow-Origin`, so third-party failures are invisible), a request that never got a response has no status, and the resource-timing buffer holds only ~250 entries - an absent block means "nothing readable failed", never "nothing failed". Do not let a doc or a prompt claim otherwise. It rides on `CaptureResult.diagnostics` into editor state (cleared when a capture starts, like `environment`) and into both prompt builders, which render a `Diagnostics:` block after the `Environment:` block **only at `Detailed` prompt detail, and only when it is non-empty** - so a prompt with nothing to report stays byte-identical to what it was before, and a `Compact`/`Standard` prompt never carries it at all (see the outputs paragraph below). It is deliberately not persisted on shares. **Uncaught page errors are not collected**: Chromium reports an error only to listeners in the world that threw, so the isolated world's `window` listener never sees the page's (measured - see `.docs/done/2026-08-24-diagnostics/`), and catching them would need a `world: "MAIN"` content script on every page load. That is a security-posture decision, recorded in `SECURITY.md`, not an implementation gap to quietly close.

**What gets scrolled:** `content.ts`'s `findScroller` picks the document when it scrolls, otherwise the largest `overflow: auto|scroll` element at least half the viewport tall (SPA shells with `html,body{overflow:hidden}` scroll an inner `<div>`; measuring only `documentElement.scrollHeight` there captured a single viewport). `PageMetrics.fullHeight`/`viewportHeight` are that scroller's `scrollHeight`/`clientHeight` and `scrollerTop` is where it starts in the viewport; `segmentPlacement` (pure, unit-tested) keeps the first frame whole so chrome above the scroller (a header) appears once and crops later frames to the scroller's rows. Scrolls use `behavior: "instant"` so a page's `scroll-behavior: smooth` cannot animate past the frame capture (which stitched the previous viewport twice). The scroller's native scrollbar is hidden (`scrollbar-width`/`::-webkit-scrollbar`) for the duration of the capture and restored afterward, so its track is not baked into the stitched frames.

**One-click auto-capture races two transient Chrome errors** (it fires the instant the editor opens, before the tab strip/content script have settled), handled by retry helpers in `capture.ts`: `activateTab` retries `chrome.tabs.update` past `isTabsBusyError` ("Tabs cannot be edited right now"), and `sendToContentScript` re-injects + retries past `isNoReceiverError` ("Receiving end does not exist"). All four are exported and unit-tested in `tests/capture.test.ts`.

**On-page capture notice:** because capture activates and scrolls the _target_ tab (the user is looking at the page, not the editor), `content.ts` injects a fixed top-of-viewport notice ("Capturing full page… don't switch tabs or scroll"). The orchestrator shows it (`SB_CAPTURE_BEGIN`), hides it for each `captureVisibleTab` frame (`SB_SET_OVERLAY`, acked only **after the next paint** via double-rAF so it never leaks into a frame), re-shows it on each `SB_SCROLL_TO`, and removes it on `SB_RESTORE_SCROLL` / `SB_CAPTURE_END`. Notice messages go through `notify` — best-effort, never abort a capture.

**The page cleans up after an abandoned capture itself.** Every capture message re-arms a `CAPTURE_WATCHDOG_MS` (8s) timer in `content.ts`; `SB_CAPTURE_END`/`SB_RESTORE_SCROLL` clear it. A running capture talks far more often than that (the countdown is one message a second, the frame loop several), so silence that long means the editor tab is gone - closed, crashed or navigated away mid-capture - and `endCapture()` removes the notice, restores the scrollbars and forgets the scroller. Only the page can notice that nobody is coming back, and the countdown widened that window from milliseconds to seconds of pure waiting. It deliberately does **not** scroll: 8 seconds is long enough for the user to have scrolled somewhere themselves, and yanking them back would be worse than the offset left behind.

**Per-annotation DOM context:** after every annotation commit the editor (`main.tsx`'s `refreshContexts`) maps each annotation back to the live tab, in **two passes**. First `toPageCoords(inspectAnchor(annotation), mapping)` gives a page CSS px point - **not** a bare `/ scale`: a visible-area capture's image starts at the scroll position it was taken from, so every point on it is `scrollOffset` further down the page than its image coordinate says (a band above the scroller is exempt - it never moved). Getting that wrong is silent and confidently wrong, which is exactly what this module's "a stale name is worse than no name" rule exists to prevent, so the mapping is pure and unit-tested. That point and one `SB_INSPECT_POINTS` round trip carries **all** the points: `content.ts` scrolls the capture scroller quietly (no notice, no scrollbar hiding, the point centred in the viewport so a sticky header cannot answer for it, original scroll restored in a `finally`), runs `document.elementsFromPoint`, skips shotback's own overlay/style nodes, marks the hit element with `data-shotback-hit="<index>"` and describes it as an `ElementContext` (`cssPath`, tag/id/classes/role/testId/text, page-px `rect`). Then `readFiberComponents` runs in the page's **own** JavaScript world (`chrome.scripting.executeScript({ world: "MAIN" })`) to read the React fiber off each marked element and clear the mark - it has to: React hangs its fiber on the DOM node as a page expando, and a content script's isolated world cannot see page expandos at all (`Object.keys(element)` is empty there; the `inner` e2e proves both halves). Results are merged by annotation id through `setAnnotations` **only**: a context is derived data, so refreshing it must never add an undo entry - which does mean an older history snapshot can carry an older context. Guards: only the newest inspection may write (a generation counter in `main.tsx`, so a slow response cannot land on top of a newer commit); the content script returns its `window.location.href` and a mismatch with the capture's `pageUrl` answers every point with `null`; a `null` answer **clears** that annotation's context rather than keeping a stale name; component names are clamped to one line of 50 chars on the extension side, and ids, classes, roles, testids and tag names are clamped to 50 chars too, since all of it is page-controlled text. The editor stamps `data-sb-inspect-gen` on its own `<body>` after each inspection writes back - purely a test hook, so the e2e can wait for a round trip instead of racing it. **The result is shown before the export, not only in it**: each comment-timeline row carries one muted, truncated line naming the element it landed on (`describeElement` in `feedback.ts` - `tag#id`, else `tag.firstClass`, else the path's last step; the whole `cssPath` on hover). `elementsFromPoint` always answers *something*, so a box a few px off its target still resolves a confident selector, and until this the first sight of it was the copied prompt. Best effort end to end: a closed tab, a non-React page or a missing content script yields no context (or no component chain), leaves what is stored alone and never surfaces an error. The prompts append ` -> <cssPath>` (and ` in <A > B>` when a component chain was found) to each area-comment line.

**Storage (two-tier, see `src/lib/localStore.ts` + `src/lib/shareDb.ts`):** share _metadata_ (annotations, feedback, page URL, blob key) lives in `chrome.storage.local` under `share:<id>` keys; the large PNG _blob_ lives in IndexedDB (`shotback`/`shareImages`) keyed by `share-image:<id>`. `localStore` is the only module that touches both; it converts dataURL↔Blob, enforces `schemaVersion: 2`, transparently migrates legacy v1 records (inline `imageDataUrl`) on read, and prunes via `DEFAULT_RETENTION_POLICY` (50 shares / 30 days) after each save. A share also carries two optional **passthrough** fields, `environment` and `previousShareId` - optional by design, so neither needed a `schemaVersion` bump or a migration, and both are simply absent on older records. A share link is `chrome.runtime.getURL("viewer.html?share=<id>")` - intentionally profile-scoped, never a public URL.

**Undo/redo** (`src/lib/history.ts` + `useEditorState`): `annotations` stays the live in-gesture state; only completed edits are snapshotted into `history`. Commit points are the canvas's `onCommit` (pointer-up after a create, move or resize - a plain selection click does not commit), the inline comment editor when it is left with a pending edit - on `onBlur` **and** on the effect cleanup that runs when the selection changes or the textarea unmounts, because clicking empty canvas removes it without React ever dispatching a blur (one entry per editing session, not per keystroke) and `removeAnnotation`, which every delete path goes through (Delete/Backspace, "Delete Selected Item", the timeline's "Remove"). A new capture calls `resetAnnotations`, which clears the history too. Both the annotations and the history are mirrored in refs that every write updates, and handlers read those refs rather than the render values - a commit can arrive from a passive effect, and the very next keypress must see it before React has re-rendered. `undoAnnotations`/`redoAnnotations` set the history and the live annotations together and drop the selection when the selected annotation is no longer there; the sidebar's Undo/Redo buttons and one window keydown listener in `annotation-canvas.tsx` (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z or Ctrl/Cmd+Y, ignored while typing in a field - the same listener that carries the V/B/A/T/R/C tool hotkeys) are the only callers.

**Pure, unit-tested helpers** (these are where the real logic and the tests live — `tests/*.test.ts` mirror them):

- `src/lib/crop.ts` - `Rect`, `MIN_CROP_SIZE` (24), `clampCrop(crop, image)` (whole px, at least the minimum per side, fully inside the image - applied both where a crop is created and again at export time) and `applyCrop(annotations, crop)`: shifts annotations from capture space into crop space, clamping a box to the visible part of itself, clamping a highlight the same way, keeping an arrow when **either** endpoint is inside (shifted, never clipped - clipping would move the head, which is what an arrow points at), keeping a pen stroke when **any** point is inside (shifted, and equally never clamped), keeping a text when its anchor is inside, and dropping everything else. Ids, comments and contexts survive; only coordinates change, and numbering is re-derived downstream so a dropped annotation leaves no gap. Also `cropViewMetrics(view, image)`, the canvas's crop-preview mapping: the offsets and width of the image wrapper as **percentages** of the crop window, plus the window's aspect ratio. Because the wrapper is absolutely positioned its `left` percentage resolves against the window's width and its `top` against the window's height, so each offset divides by its own axis of the view - and because every number is a ratio, **one wrapper mapping serves both zoom modes** with nothing measured in JavaScript: at 1:1 the window is exactly the view's pixel size, so the percentages evaluate to `-view.x`/`-view.y` and the image's natural width; at fit-width the window is fluid and they scale with it. Only the window's own style differs between the two (fixed px vs `width:100%` + `max-width` + `aspect-ratio`).
- `src/lib/annotate.ts` - `exportAnnotatedImage` rasterizes annotations onto the screenshot as **numbered pins** (circle + number at `pinCenter`, sized by `pinRadius`) and appends a **"Notes" legend footer**: one row per numbered annotation, led by the same coloured pin and carrying `noteText` (the prompt's own wording, placeholders included), then the general-feedback paragraph. `selectFeedbackRenderMode` picks footer vs. overlay so the export canvas never exceeds `MAX_EXPORT_CANVAS_HEIGHT`/`AREA` limits (the overlay card renders the same content, truncated). An optional `crop` draws **only** that source rect onto a crop-sized canvas and sizes the pins, layout and footer decision off it - it never calls `applyCrop` itself: the caller passes annotations already in crop space, so the image and the text outputs cannot describe different lists. Redactions are pixelated onto the base image **before** any of that is drawn (see the Redact paragraph below); `pixelateRegion(ctx, source, region, size)` is **exported** and takes any `CanvasImageSource`, because the editor canvas paints the same blocks live - one helper, so the preview and the burned-in export cannot drift. `redactionBounds(region, size)` is exported beside it (and is what `pixelateRegion` clamps with), because the canvas has to copy back exactly the rects it touched and re-deriving that rounding by hand is how the two would start disagreeing by a pixel. `arrowHeadPoints` is exported and drawn by the canvas too (as an SVG `<polygon>`), so on-screen and exported arrowheads cannot drift - as are `HIGHLIGHT_ALPHA` and `HIGHLIGHT_EDGE_WIDTH`, for the same reason.
- `src/lib/numbering.ts` - `numberAnnotations` (creation order, the **one** numbering shared by the comment timeline, the prompt, the canvas pins and the exported image; it **excludes redactions**, once, so every one of those surfaces skips them together), `redactions` (the other half of that split, in creation order), `inspectableAnnotations` (what may be mapped back onto the live page - redactions filtered out here rather than at the call site; `numberAnnotations` numbers whatever list it is handed), `viewPins(annotations, crop, image)` (the pins **as the exports will draw them**, translated back into capture space for the canvas overlay: with no crop it is the plain list, and with one applied it is `applyCrop`'s survivors, renumbered, with `pinRadius` and `pinCenter` taken from the crop's own canvas and the centres shifted by the crop origin - so a pin can no longer be numbered 3 on the canvas and 2 in the PNG, or drawn half-clipped on one and clamped a full radius in on the other; an annotation the crop dropped gets no pin at all, exactly as the export drops it. The canvas chip says how many are excluded), `pinRadius` (clamped to the capture width), `pinAnchor` (box corner / arrow tail / text baseline start), `inspectAnchor` (the point an annotation _means_ - box centre, arrow tail, text start - fed to `SB_INSPECT_POINTS`), `pinCenter` (that anchor clamped to `[r, width - r] x [r, height - r]`, used by both draw sites so an edge pin is never clipped), `describeGeometry` (per-tool position in image px plus % of page, rounded, for the prompt's per-annotation line - a highlight reads like a box, a pen as `pen path of N points from (..) to (..)`; **every printed number is clamped to the image** by `clampToImage`, the same helper the sidecar reports its rect through, because a crop keeps an arrow's head and a pen's stray points outside the image and a prompt that says `at (-40, 12)` describes pixels the attached file does not have - and disagrees with the JSON beside it), `clampToImage` (that clamp, exported here and imported by `sidecar.ts`, so there is one) and `annotationBounds` (the rectangle an annotation occupies; a text run is estimated from its length, a pen stroke is min/max of its points - it lives here rather than in `src/editor/` so `src/lib/sidecar.ts` can use it without `lib` importing `editor`).
- `src/lib/feedback.ts` - `buildExternalLlmPrompt` / `buildClaudeCodePrompt` (the structured prompts copied for the cloud-LLM and Claude Code exports; both take an optional `CaptureEnvironment` and an optional `PageDiagnostics`, plus an optional `Verbosity` (`"compact" | "standard" | "detailed"`, default `"standard"`) that controls how much of that context actually renders - see the outputs paragraph below), `annotationSummary`, `describeElement` (the one-line element name the comment timeline shows - see the DOM-context paragraph; it lives here rather than beside `cssPath` for the chunking reason in the `dom-context.ts` bullet below) and `noteText` - the single wording for an annotation's note, shared with the exported legend and with the JSON sidecar. `buildClaudeCodePrompt` also takes an optional `sidecarPath` and renders the `Machine-readable annotations (selectors, rects, diagnostics): <path>` line right under the image path, omitting it entirely when no sidecar was written. It also takes an optional `followsPrevious`, which adds the one before/after line under those paths for a re-capture session (see the re-capture paragraph below). `buildBatchPrompt(entries, sidecarPath)` is the batch equivalent - the JSON path first, then a numbered index of captures - see the batch-handoff paragraph below.
- `src/lib/prefs.ts` - `getPrefs()`/`setPrefs(partial)`, a thin `chrome.storage.local["prefs"]` wrapper (tolerates a missing or corrupt stored value, merges a partial write) in the style of `localStore.ts`'s storage helpers. Currently holds one field, `promptVerbosity`.
- `src/lib/capture.ts` - `buildScrollSteps` (scroll offsets), `segmentPlacement` (where each frame lands on the stitched canvas), `buildEnvironment` (page metrics + user agent + `now` -> `CaptureEnvironment`), `CaptureMode`/`CAPTURE_MODES`/`CAPTURE_DELAY_SECONDS`/`captureOptions` (the chooser's three options, and the two things the orchestrator actually takes) , `captureNoticeHeading` (the countdown wording) and `toPageCoords(point, mapping)` (a stitched-image point as the page's own CSS px, which is where `scrollOffset` is applied), plus the retry helpers/guards `activateTab`, `sendToContentScript`, `isTabsBusyError`, `isNoReceiverError`, the best-effort `inspectPoints(tabId, points, pageUrl)` and `getDiagnostics(tabId)` wrappers and `readFiberComponents` (the self-contained function injected into the page's own world - it must reference nothing outside itself, because Chrome serializes its source).

The content script is a classic script (only the service worker is `"type": "module"`), so the moment a helper here is also imported by the editor, Vite emits this file as a shared chunk and `dist/content.js` starts with a top-level `import` it cannot execute: the script silently never loads and *every* capture dies with "Receiving end does not exist", nowhere near the change that caused it. That is why `describeElement` lives in `feedback.ts`, and why the first e2e test now asserts the built `content.js` carries no `import`.
- `src/lib/sidecar.ts` - `buildSidecar` builds the `Sidecar` JSON written beside the PNG for the Claude Code handoff: `version: 1`, the capture metadata, the annotations numbered by `numberAnnotations` (so the JSON, the prompt, the pins and the timeline agree), each with `noteText`, an `annotationBounds` `rect` in image px **clamped to the image** (`clampToImage`, which now lives in `numbering.ts` beside `describeGeometry` - one clamp, so the JSON and the prose beside it cannot describe an annotation differently) - the stored geometry is deliberately not clamped, since `applyCrop` keeps an arrow's head and a pen's stray points outside the crop rather than redrawing the shape, but the rect the JSON _reports_ answers "where is this on the attached image" and so cannot describe pixels the image does not have - a `normalizedRect` (0..1 of the image, guaranteed in range by that clamp, 4dp, `0` rather than `Infinity` when no capture has sized it yet) and the `ElementContext` when one was read, plus a `redactions` array (`{ tool, rect, normalizedRect }`, no `n`/comment/context, omitted when nothing was hidden), the `environment`/`diagnostics` passthroughs and the relative `imagePath`. Pure: every value comes from the caller, and optional fields are omitted rather than serialized as `null`. `buildBatchSidecar(captures)` wraps several of those into the `BatchSidecar` (`{ version: 1; captures: Sidecar[] }`) written once per batch export.

**Design system (`src/components/ui/*` + `src/styles/globals.css` + `tailwind.config.js`):** components are driven by semantic HSL **CSS-variable tokens** (`--primary`, `--secondary`, `--muted`, `--accent`, `--destructive` + `-hover`, `--border`, `--input`, `--ring`, plus `--glow-1`/`--glow-2` for the body gradient and `--card-highlight`/`--card-shadow`/`--button-highlight` for elevation) mapped to Tailwind color utilities - use `bg-primary`/`border-input`/`ring-ring` etc., never hardcoded `emerald-*`/`slate-*`/`bg-white` literals, anywhere in `src/` (`grep -rnE "(text|bg|border|ring|from|to|via|fill|stroke)-(slate|emerald|red|white)\b" src/` must stay at zero hits; the `hover:`/`focus:` variants are covered because the prefix still follows the colon). **Dark applies two ways:** automatically from `@media (prefers-color-scheme: dark)` on `:root:not(.light)`, and explicitly via `class="dark"` on `<html>`; `class="light"` forces light back on. The two blocks hold the same 27 custom properties plus `color-scheme` and are **deliberately duplicated** - `light-dark()` returns a colour rather than the bare HSL channels the tokens interpolate (breaking `bg-primary/40`-style alpha modifiers) and an inline pre-render script is forbidden by MV3's CSP. Both live **outside `@layer base`** so Tailwind does not tree-shake the unreferenced selectors. `tests/e2e/extension.spec.ts` guards a slice of this: "dark theme keeps every control legible" loads an **empty** `editor.html` with `colorScheme: "dark"`, walks every `button, p, span, h1, h2, label` that has text, and fails if its colour is within 0.3 luminance of the nearest painted ancestor background, or if the body background is still the light value. It never mounts the comment timeline, saved shares, the annotation-canvas branch or the viewer - the visual checks recorded in `.docs/done/2026-08-24-dark-theme/completion-summary.md` are the evidence for those. `Select` is a **custom WAI-ARIA listbox** (not a native `<select>`): pass `value` + `onValueChange` + `options`, not `<option>` children - the native option popup is unstylable, which is why it was replaced.

**Redact (hide a region):** the palette's `Redact` segment (`R`) draws a `RedactAnnotation` (`{ tool: "redact"; x; y; width; height }`) into the same `annotations` array and the same undo history as a box, so it moves, resizes, deletes and undoes exactly like one. Everything else about it is deliberately mute: `numberAnnotations` filters it out (no pin, no timeline row, no legend row, no numbered prompt line), `inspectableAnnotations` filters it out of the inspection list in the lib rather than at the call site (reading the element under it would put its selector and its text into the prompts it exists to keep them out of, so a second call site cannot leak by default), and it gets no inline comment editor - its `comment`/`context` are typed `never`, so the compiler, not the UI, is what enforces "never populated". Picking it enters draw mode the way every other tool does, and (like Crop) an existing annotation does not swallow the pointer-down, so a secret is coverable wherever it sits. On the canvas the region is **pixelated live**: `annotation-canvas.tsx` renders one `<canvas id="redaction-overlay">` inside the image wrapper (sized in image px, stretched `inset-0 h-full w-full` exactly as the SVG is so it tracks fit-width and 1:1 alike, `pointer-events-none`, and **below** the SVG so pins and handles still draw on top), redrawn by an effect on `[annotations, baseDataUrl, crop, imageSize, revealedId]` that **reproduces the export's canvas step for step**: an offscreen buffer sized to the clamped crop (or the whole capture), the annotations put through `applyCrop` exactly as `exportView` does, then the same exported `pixelateRegion` over each region **in order, reading the buffer as the region before it left it**. Only the rects `redactionBounds` says were touched are copied onto the overlay, shifted back into display coordinates - which is what keeps the overlay transparent wherever the capture is untouched. Calling the shared helper is not enough on its own, and both shortcuts are covered by tests: a redaction the crop **cuts through** is clipped by `applyCrop` and blocks from the crop's edge, so pixelating the un-clipped region off the pristine `<img>` lands a different block grid (`tests/annotate.test.ts` proves the seams differ at `crop.x = 505`; the e2e compares the overlay's pixels against the saved share's for a crop that cuts a region, and fails at a mean delta of 5.7 if the view is ignored); and **overlapping** redactions stack in the export but would each read pristine pixels otherwise. With no redactions the overlay is sized to 0x0 rather than holding a capture-sized backing store. Sizing the canvas clears it, which is how an undone, deleted or moved redaction stops being drawn; `onLoad` sets a fresh `imageSize` object, so a second capture of identical dimensions still re-runs it. The diagonal hatch is now only the **selected** region's fill (plus the in-progress draft's), because it is the pixelation, not a hatch, that says what the export will contain. Holding **Alt** with a redaction selected drops both the hatch and its pixelation from the overlay so the original shows through, and letting go covers it again - the one way to check "is enough of that address covered?" without writing the file first. **The hiding itself is one place**: `exportAnnotatedImage` draws the base image, pixelates every redaction through a `ceil(w/12) x ceil(h/12)` offscreen buffer (downscaled at `imageSmoothingQuality = "high"` so a block weighs its whole area instead of sampling a pixel out of it, redrawn with `imageSmoothingEnabled = false`), and only then draws annotations, pins and the legend, so nothing can be painted over a secret before it is destroyed. Since **every** output is that function's data URL - download, Copy Image, the cloud package, the Claude Code PNG and the image `saveLocalShare` stores - there is no path a raw capture can leave by. `applyCrop` shifts and clamps a redaction like a box. The prompts add one `Redacted regions: N` line at **every** verbosity (a safety fact is worth one line even in `Compact`), and the sidecar lists them under `redactions` as `{ tool, rect, normalizedRect }` with no `n`, comment or context. `SECURITY.md` carries the honest statement of what that does and does not protect: the unredacted capture lives only as the editor tab's in-memory `baseDataUrl` and is gone when the tab closes.

**Crop (region export):** the palette's last segment is `Crop` (`C`) (`EditorTool = AnnotationTool | "crop"` in `src/lib/tool-palette.ts` - nothing stored in an `Annotation` can ever be a crop). Drawing with it sets `cropDraft` (clamped by `clampCrop`, discarded under `MIN_CROP_SIZE`). Both `crop` and `cropDraft` live **outside** the annotation history, next to `zoom`: a crop is a view onto the capture, not an edit of it, so undo never steps through one - and a new capture clears both (`main.tsx`).

**Every crop control is on the canvas, none in the sidebar** (two sidebar rows used to appear the moment a marquee was drawn and vanish the moment it was applied, shoving ~52px of controls up and down). A marquee awaiting Apply is dimmed around, outlined (`#crop-region`) and carries **eight resize handles** - `renderHandles` in `annotation-canvas.tsx`, the same `applyBoxResizeDelta`/`BOX_RESIZE_HANDLES` a box uses, bounded by the image at `minSize: MIN_CROP_SIZE` and written back through `clampCrop`; resizing a marquee commits nothing to the history. **Apply crop / Cancel** float just inside the marquee's bottom-left corner, anchored in percentages of the crop window and `clamp()`ed on both axes against the bar's own fixed size, so a marquee at the window's right or top edge cannot push the bar out of the clipped window. **Enter** applies a drawn marquee from the keyboard (the counterpart to Escape cancelling one), through the same `applyCropDraft` the button uses - so the bar is never the only affordance. Apply, Cancel and Clear all carry `disabled={isBusy}`, like every other control that changes what an export will contain: an export promise in flight captured the crop it started with. They are plain HTML over the window, deliberately **not** a `foreignObject` in the SVG (the inline comment editor's trick): SVG content is sized in _image_ px, so at fit-width the buttons shrank with the capture to well under a readable and tappable size. Anchoring them _inside_ the marquee means they can never be clipped by the window.

**Once applied, the canvas shows the crop and nothing else** - no dim, no marquee, no `#crop-region`; the applied region is stated by a `Cropped to WxH` / **Clear** chip over the canvas (bottom-left, `pointer-events-none` with only its button opting back in, so it cannot make a corner of the capture undrawable) and by `data-crop="x,y,w,h"` on `#capture-window` (a test affordance in the style of `data-sb-inspect-gen`). The preview is a third box between the scrollport and the image: `#capture-viewport` > `#capture-window` (`relative overflow-hidden`, sized to the view, `mx-auto` so a region narrower than the pane is centred rather than pinned left) > the image wrapper (absolute, offset and scaled by `cropViewMetrics`) > the `<img>` and the SVG overlay. **The image and the overlay are never resized or re-`viewBox`ed by a crop** (a deliberate departure from the original brief's "the SVG overlay viewBox switches to the crop rect" - keeping the full image's viewBox is what preserves the overlay-covers-image invariant and leaves annotation coordinates, `getScreenCTM` pointer math and `refreshContexts` untouched; the e2e pins the pointer round trip at 1:1 with a crop applied) - the overlay keeps covering the whole capture exactly, which is what annotation coordinates, `refreshContexts` and pointer hit-testing depend on; annotations outside the crop are simply clipped by the window, exactly as the exports drop them. The e2e's `overlayMatchesImage` guards that invariant with a crop applied and again after Clear. **Annotations are stored uncropped**: the shift happens once, at output time, in `exportView(state)` (`use-exports.ts`) - the single derivation every output goes through, handing back `applyCrop(annotations, crop)`, the clamped crop and the crop's size as the reported image size (and, with no crop, the untouched state, so every output stays byte-identical to before). That is also why `refreshContexts` keeps working: it maps `inspectAnchor`/`captureScale` back onto the live tab in **capture** coordinates, which a crop never disturbs.

**Four outputs from the editor:** all four render `exportView(state)`, so an active crop applies to every one of them. The sidebar's `#editor-actions` column states one hierarchy and one order: the **edit** group (Undo/Redo, Delete Selected Item), a `Separator`, the **send** group - **Copy for Claude Code** (the only `variant="default"` button on the page once a capture exists, with a one-line muted caption under it naming the format actually in force, so the JPEG pref cannot leave it promising a PNG), Prepare for Cloud LLM, Copy Local Share Link - another `Separator`, then the **file** group (Download Image, Copy Image). Everything else is `secondary`, and **Capture Page** is primary only until `baseDataUrl` is set, after which it steps down: two filled buttons in one column is no recommendation at all. The e2e asserts both the count of `.bg-primary` inside `#editor-actions` and the column's full label order. The outputs themselves are: (1) _Copy Local Share Link_ → `saveLocalShare` + viewer URL; (2) _Prepare for Cloud LLM_ → downloads the annotated PNG and copies `buildExternalLlmPrompt` output to the clipboard; (3) _Copy for Claude Code_ → saves the PNG **and a JSON sidecar** (`cap-<ts>.png` / `cap-<ts>.json`, same timestamp) to `Downloads/shotback/` via `chrome.downloads`, **also records the capture in Saved Shares** (`saveShareForExport`, the same `saveLocalShare` path `createShareUrl` uses, `environment`/`previousShareId` passthrough included) so the tool that wrote the files can still show you the capture once the clipboard is gone - best effort like the sidecar, with its own line in the status when it fails, and the share is always PNG (`exported` is reused when the format pref already is one, re-rendered when it is JPEG, because the batch handoff writes every share out as `cap-<i>.png`). It does **not** put the share URL on the clipboard: the clipboard holds the prompt. It reads back both absolute paths and copies `buildClaudeCodePrompt` output with the paths translated by `toClaudePath` (`src/lib/wslPath.ts`, `C:\… → /mnt/c/…`) so a WSL Claude Code session can read the files directly. The sidecar (`buildSidecar`, `src/lib/sidecar.ts`) is the machine-readable half of the same review, and the prompt points at it on its second line (`Machine-readable annotations (selectors, rects, diagnostics): <path>`). It is **best effort**: `saveSidecar` in `use-exports.ts` swallows its own failures, the prompt then simply carries no sidecar line, and the status says so rather than claiming a clean copy. `skills/shotback/SKILL.md` is the companion skill users copy into their own project, telling an agent to read the sidecar instead of pixel-hunting; (4) _Copy Image_ → `copyImage` in `use-exports.ts` writes the annotated PNG straight to the clipboard (`navigator.clipboard.write` with a `ClipboardItem`) for pasting into any agent chat - no download step. The extension makes **no network requests of its own**; data leaves the device only via these explicit manual exports.

**Sidebar minors that are load-bearing:** the annotation count is stated **once**, as the sidebar header's `Badge` (`plural(noteCount, "note")`) - the old `Annotations: N` line is gone and the comment timeline's heading dropped its count badge, so there is a single number to trust rather than two that can disagree. `plural(count, singular, pluralForm?)` in `src/lib/utils.ts` is the one pluralisation rule (`tests/utils.test.ts`); "1 notes" cannot come back by hand. A created share link is **not printed**: it goes on the clipboard and the sidebar shows a `Local share link copied` chip with an **Open** anchor (styled with `buttonVariants`, so it is a real link - middle-click, new tab), and `state.setShareUrl("")` at the top of every other export clears it, so the chip can never label the wrong clipboard. The **saved-shares list follows the store, not just this tab's own writes**: `use-exports.ts` subscribes to `chrome.storage.onChanged` and re-lists whenever a `share:` key changes (only `share:` keys - `prefs` writes on every dropdown change). Two editor tabs are the normal way to build a batch, and a list read once on mount left the first tab showing one share with no way to pick up the second: the only refresh was a reload, which re-runs `autocapture=1` and destroys that tab's annotations. The panel's toggle also carries the count while collapsed (`Show (N)`), so "did that save?" is answerable without expanding it. Saved-share rows lead with the stored `environment.pageTitle` (falling back to `shareLabel(pageUrl)`'s hostname) beside a 40px `loading="lazy"` thumbnail - an object URL over the stored blob via `getLocalShareImageUrl` in `localStore.ts` (`shareDb` stays behind that module). That map is **diffed, never rebuilt**: `shares` is a fresh array after every refresh, so tearing it down on identity change made one delete blank every row to grey and re-read every blob. Only ids that left are revoked, only missing ids are loaded, and everything is released on unmount. Destructive actions confirm **in place**, never through `window.confirm`: `useTimedConfirm<T>(ms)` (`src/editor/use-confirm.ts`) arms a key that disarms itself on a timer, so **Capture Page** with annotations on screen swaps to a `Replace capture?` / `Cancel` pair for 5s and a saved share's **Delete** swaps to `Confirm` / `Cancel` for 3s. The keyboard hazards are handled in the hook rather than at each call site, because they are identical at both: the pair **replaces** the trigger, so confirming, cancelling or simply waiting out the timer unmounts whatever had focus. `triggerRef(key)` re-focuses the trigger when the pair goes, but only when focus was orphaned onto `document.body` (a timed revert must not yank the caret out of a field someone is typing in); `onKeyDown` makes Escape cancel; and `onConfirm(run)` ignores activation for the first 250ms after arming, so a double-click's second half cannot land on a destructive button that was not there when the press began. All three are covered in the e2e.

**Batch handoff (a fifth output, from the saved-shares panel):** `src/editor/saved-shares.tsx` gives every saved share a checkbox and, once at least one is ticked, a **"Copy batch for Claude Code"** button; the selection is local state, but the ids handed out are derived from the live `shares` list, so a share deleted while ticked cannot linger in a batch. `copyBatchForClaudeCode(ids)` in `use-exports.ts` writes each share's stored PNG to `Downloads/shotback/batch-<ts>/cap-<i>.png` and one `batch.json` beside them (`buildBatchSidecar(captures)` in `src/lib/sidecar.ts` - `{ version: 1; captures: Sidecar[] }`, a pure wrapper that only stamps the version), then copies `buildBatchPrompt(entries, sidecarPath)` (`src/lib/feedback.ts`): the JSON path first, then one numbered line per capture carrying its page URL, annotation count and image path. Per-capture detail lives in the JSON, not in the prompt, so a ten-capture batch stays readable. Each capture's `Sidecar` is built by the same `buildSidecar` from the **stored share** (its annotations, environment, feedback and page URL; `capturedAt` falls back to `createdAt`, `imagePath` is the batch-relative `cap-<i>.png` so the folder is portable, `imageFormat` is always `"png"` because a share always is, and `diagnostics` is absent because shares never persisted it). A share's image is already annotated, so nothing here re-renders it; the only reason it is decoded (`decodeImageSize`) is to size `normalizedRect`, since shares predate crop and carry no dimensions. Unlike the single-capture handoff, this one is **all-or-nothing**: the loop is sequential and the first share that cannot be read or written throws, so no prompt is copied and the error status names the failure and the folder that may hold leftovers.

**Re-capture (before/after):** every row in the saved-shares panel has a **Re-capture** button. `recaptureShare` (`src/editor/recapture.ts`) opens that share's `pageUrl` in a new tab, waits for it to report `status === "complete"` (polled every 250 ms, bounded at 15 s - a timeout proceeds rather than throwing, because the capture re-injects the content script and retries by itself), then opens a second editor on that tab with the **same URL shape `background.ts` builds for the toolbar icon**, plus `previousShareId=<id>`. The new session reads that param in `main.tsx` and hands it to `useExports`, which does two things with it and nothing else: `saveLocalShare` records it on the share saved from that session, and `buildClaudeCodePrompt` gets `followsPrevious: true`, adding one line under the paths (`Before/after: this capture follows an earlier one - verify the fix against the previous state.`). It is a flag, not a path: the previous PNG lives in the share store, not in Downloads. The viewer resolves the predecessor with `getLocalShare` **best effort** - a deleted or pruned one degrades to the new capture plus a muted note, never an error - and one step only: it does not walk a chain. There is deliberately **no image diffing**: two captures taken at different scroll positions and window sizes would make a pixel diff noise, so the feature is side-by-side and nothing more.

Both prompt outputs (2 and 3) are shaped by the sidebar's **"Prompt detail"** setting - `Compact` (numbers, notes, general feedback and the page URL only), `Standard` (the default; everything above plus the `Environment:` block, per-annotation geometry and the element each annotation covers) or `Detailed` (standard plus the `Diagnostics:` block and, under each annotation with one, its element's `text`/`classes`/`rect`). `useEditorState` loads it from `src/lib/prefs.ts` on mount and persists every change, so it carries across sessions; `use-exports.ts` passes it straight through as `verbosity` on both builder calls.

**JPEG export:** the sidebar's **"Export format"** setting (`png` default, `jpeg`) is loaded from and persisted to `src/lib/prefs.ts` exactly like `promptVerbosity`. Outputs (2) and (3) and the plain **Download Image** button pass it as `format` (and the fixed `DEFAULT_JPEG_QUALITY`, 0.9 - there is no quality control in the UI) to `exportAnnotatedImage` (`src/lib/annotate.ts`), which fills the canvas white before drawing when `format` is `"jpeg"` (JPEG has no alpha channel, so an untouched region would otherwise encode black) and calls `canvas.toDataURL("image/jpeg", quality)` instead of the PNG default. **Copy Image and the saved share/viewer are always PNG** - `copyImage` never passes `format` at all, with a comment explaining why (`ClipboardItem` support for `image/jpeg` is inconsistent across browsers), and `createShareUrl` likewise. Every filename that carries an extension swaps `.png` for `.jpg` through `use-exports.ts`'s own `extFor`; the sidecar (`buildSidecar`) gets a matching optional `imageFormat` field, `version` unchanged at `1`. A muted sidebar line, **"Last export: N KB"**, reads `EditorState.lastExportSize` - set from `dataUrlByteLength` (`src/lib/annotate.ts`, the base64 payload's own length, so it needs no `fetch`/`Blob` round trip and runs in the unit tests too) right after every export builds its data URL, PNG or JPEG alike, and cleared when a new capture starts.

## Conventions

- TypeScript `strict` with `noUnusedLocals`/`noUnusedParameters`; explicit over clever.
- `kebab-case` file names; small, low-blast-radius diffs over broad refactors.
- Keep pure logic in `src/lib/*` (testable, no `chrome.*`); confine `chrome.*` calls to the editor/viewer/background/content boundaries.
- Conventional-commit style messages (`feat:`, `fix:`, `chore:`, `security:`); one logical change per commit.
- Permissions are deliberately minimal (`activeTab`, `tabs`, `scripting`, `storage`, `unlimitedStorage`, `downloads`, `<all_urls>` host access) - see `SECURITY.md` before touching `public/manifest.json`.
